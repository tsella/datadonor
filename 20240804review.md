# DataDonor — Bug Review

**Date:** 2026-08-04
**Scope:** `server/` (Node/Fastify/SQLite) and `client/` (SwiftUI/HealthKit iOS app)
**Reviewed at commit:** `53da941`

> **Status: all findings fixed** (2026-08-04). See "Remediation log" at the end of this
> document for what changed and how each fix was verified. The findings below are kept as
> written at review time, describing the code before the fixes.

Findings are ordered by severity. Each entry names the file and line, describes the
concrete failure, and proposes a fix. Items marked **[verified]** were reproduced with a
runnable snippet during the review; the rest are read-through findings.

## Critical

### C1. Secrets and health data are untracked but **not** git-ignored — leak risk on next `git add -A`

**Files:** `.gitignore`, `server/health_sync.db`, `server/copy.json.example.json`

`.gitignore` ignores `server/data/` and `server/config.json`, but the working tree
contains two untracked files that fall outside those patterns:

- `server/health_sync.db` — a live SQLite database of personal health records. `git check-ignore`
  returns non-zero for it, confirming it is **not** ignored. **[verified]**
- `server/copy.json.example.json` — appears to be a stray copy of the config template.

A routine `git add -A && git commit` publishes a database of biometric data to a public
GitHub repository. For a project whose README explicitly centers on health-data privacy,
this is the highest-impact issue in the tree.

Note also that `db.js` resolves its path from `config.database.path` (default
`./data/datadonor.sqlite`), so `server/health_sync.db` is a *second*, stray database — it
is likely a leftover from an earlier default. Its presence outside `server/data/` is
exactly why the ignore rule misses it.

**Fix:** add `*.db`, `*.sqlite`, `*.sqlite3` and `server/copy.json.example.json` to
`.gitignore`; delete the stray `health_sync.db` after confirming it holds nothing needed;
verify with `git status --porcelain` that no data file is listed. Consider also adding a
pre-commit hook rejecting `*.sqlite*`.

### C2. Analytics counters permanently over-count on any retried or duplicate payload

**File:** `server/app.js:94-144`

The metric insert is idempotent:

```js
INSERT INTO health_metrics (...) VALUES (...) ON CONFLICT(uuid) DO NOTHING
```

but the aggregation UPSERT immediately below is **not** — it adds the payload's count
unconditionally:

```js
INSERT INTO daily_sync_stats (...) VALUES (?, ?, ?, ?)
ON CONFLICT(device_id, date_bucket, data_type)
DO UPDATE SET record_count = record_count + excluded.record_count
```

`daily_sync_stats` counts *payload rows*, not *inserted rows*. Any duplicate delivery
inflates the chart permanently. Reproduced: posting the same single-record payload twice
yields 1 row in `health_metrics` but `record_count = 2` in `daily_sync_stats`. **[verified]**

This is not a rare edge case. Duplicates are the normal path here:

- `SyncEngine.sync` uses a **background** `URLSession`, which retries on its own after
  network failures — the app never learns a retry happened.
- `HealthQueryManager.exhaustQuery` (line 200-202) saves the anchor *immediately* after
  `sync()` returns, but `sync()` only **enqueues** the upload (see C3). If the upload
  later fails, the anchor has already advanced — and if it succeeds twice, both are counted.
- `performSync` overwrites local anchors from the server on every run (line 283-295); when
  the server has no checkpoints it triggers a **full re-sync** of all history, re-posting
  every record and doubling every bucket.

**Fix:** make the counter derive from actual insertions rather than payload size. Either
use `changes()` per row and aggregate only successful inserts, or drop the incremental
counter entirely and compute stats with a `GROUP BY` over `health_metrics` (an index on
`(device_id, date_bucket)` makes this cheap). A stopgap is running
`npm run rebuild-stats`, but that only masks drift until the next duplicate.

### C3. `sync()` reports success before the upload happens — anchors advance on data that was never delivered

**Files:** `client/Sources/Managers/SyncEngine.swift:93-109`, `client/Sources/Managers/HealthQueryManager.swift:197-223`

`SyncEngine.sync` calls `task.resume()` and returns immediately. It is declared
`async throws` but never awaits the result — the comment at line 107 acknowledges this
("fire and forget"). The only failure signal is `urlSession(_:task:didCompleteWithError:)`,
which just writes a log line.

The caller treats the return as confirmation of delivery:

```swift
try await syncEngine.sync(payload: payloadData, serverURL: serverURL, apiKey: apiKey)
self.saveAnchor(newAnchor, for: sampleType.identifier)   // <- advances regardless
anchor = newAnchor
```

Consequences:

1. **Silent data loss.** If the server returns 401/403/500 or the upload fails after
   retries, the anchor has already moved past those samples. The next sync starts *after*
   them; they are never re-sent. Because the anchor is also pushed to the server as a
   checkpoint, the loss becomes permanent on both sides.
2. **Unbounded queueing.** The `while hasMoreData` loop spawns one upload task per
   1000-sample batch with no backpressure. An initial full-history sync enqueues thousands
   of concurrent background uploads at once.
3. **`totalRecordsSynced` counts enqueued, not stored, records** (line 210-214), so the UI
   overstates progress.

**Fix:** make delivery observable before advancing the anchor. The cleanest correction is
to bridge the delegate callback into the async call — hold a
`[Int: CheckedContinuation]` keyed by `taskIdentifier`, resume it in
`didCompleteWithError` / `didReceive response`, and only `saveAnchor` on a 2xx. If
fire-and-forget must be kept for true background operation, persist a pending-batch
queue on disk and only retire an anchor once its batch is acknowledged.

## High

### H1. Records with no UUID are duplicated on every sync

**File:** `server/app.js:97,109`

`uuid` is declared `TEXT UNIQUE` (`db.js:47`), and the insert relies on
`ON CONFLICT(uuid) DO NOTHING`. In SQLite, **`NULL` is never equal to `NULL`**, so a
`UNIQUE` constraint does not deduplicate `NULL`s and the conflict clause never fires.
Verified: inserting two rows with `uuid = NULL` produces two rows. **[verified]**

The client passes `metric.uuid || null` and `HealthDataPoint.uuid` is `String?`, so a
missing UUID reaches the server as `NULL`. Every re-sync of such a record inserts a fresh
duplicate, unbounded.

In practice `mapSample` always sets `sample.uuid.uuidString`, so this is currently latent
— but the server accepts arbitrary clients and the schema permits it.

**Fix:** reject payload entries without a `uuid` with HTTP 400, and/or declare the column
`uuid TEXT NOT NULL UNIQUE` so the constraint is enforceable.

### H2. Week bucketing in `/stats` splits each week across two buckets

**File:** `server/app.js:196-198`

```sql
date(date_bucket, 'weekday 1', '-7 days')
```

SQLite's `weekday 1` advances to the *next* Monday, but is a **no-op when the date is
already a Monday**. So a Monday maps to itself minus 7 days... no — it maps to itself
(`weekday 1` doesn't move, then `-7 days` goes back one week), while Tue–Sun map to the
*following* Monday minus 7 days, i.e. the Monday that starts their week. The two disagree.

Verified output: **[verified]**

| `date_bucket` | computed week |
|---|---|
| `2026-08-03` (Mon) | `2026-07-27` |
| `2026-08-02` (Sun) | `2026-07-27` |
| `2026-08-04` (Tue) | `2026-08-03` |

Monday `08-03` and Tuesday `08-04` — the same calendar week — land in **different**
buckets, and Monday is grouped with the preceding week. Every weekly chart is wrong.

**Fix:** use an unambiguous week start, e.g.
`date(date_bucket, '-' || ((strftime('%w', date_bucket) + 6) % 7) || ' days')`
for Monday-based weeks. Note this code path is currently unreachable from the app —
`DashboardView` only ever requests `timeScale: "months"` — but `weeks` is a public API.

### H3. Background sync is never scheduled — the feature does not run

**Files:** `client/Sources/Managers/BackgroundSyncManager.swift:18-28`, `client/Sources/AppDelegate.swift:10-21`

`registerBackgroundTasks` is called at launch, but `scheduleAppRefresh()` is only invoked
from **inside** `handleAppRefresh` (line 32) — the handler that fires when a scheduled task
runs. Nothing ever submits the first request. Confirmed by grep: the only call sites are
the definition and the self-reschedule.

Since no `BGAppRefreshTaskRequest` is ever submitted, `handleAppRefresh` never fires, so
the self-reschedule never runs either. Background sync is dead on arrival despite the
`BGTaskSchedulerPermittedIdentifiers` entry in `Info.plist`. The README's claim of
"automatic background syncs" is not met.

**Fix:** call `BackgroundSyncManager.shared.scheduleAppRefresh()` in
`didFinishLaunchingWithOptions` and again on `applicationDidEnterBackground`.

### H4. Background task uses only the manual override URL and a launch-time API key

**File:** `client/Sources/Managers/BackgroundSyncManager.swift:42-44`

```swift
let customURLString = UserDefaults.standard.string(forKey: "customServerURL") ?? ""
let serverURL = URL(string: customURLString)
```

Two defects:

1. Users relying on mDNS discovery (the documented default — `SettingsView` says "Leave
   blank to use automatic mDNS discovery") leave `customServerURL` empty, so `serverURL`
   is `nil` and `performSync` bails at line 254. Background sync is a no-op for exactly
   the users following the recommended setup. It cannot fall back to
   `activeServerURL` because that lives in a `ServerDiscoveryManager` the background task
   has no reference to.
2. `apiKey` is captured **once** at `didFinishLaunchingWithOptions`
   (`AppDelegate.swift:16`) and closed over for the process lifetime. A user who sets or
   changes their key in Settings — including via the QR scanner, the documented flow —
   keeps syncing with the stale value until the app is force-quit and relaunched. Every
   background request 403s.

**Fix:** read both values from `UserDefaults` at execution time inside `handleAppRefresh`,
and persist the last-approved discovered server URL so the background path can use it.

### H5. `URL(string:)` on an invalid override silently syncs to the wrong destination

**Files:** `client/Sources/ContentView.swift:144-149, 186-191`

```swift
let overrideURL = URL(string: customServerURL)
await healthQueryManager.performSync(serverURL: overrideURL ?? serverDiscoveryManager.activeServerURL, ...)
```

`URL(string:)` returns non-nil for many strings that are not usable absolute URLs —
notably a bare host or path like `"192.168.1.5:8443"` or `"myserver"`. Such a value
produces a non-nil relative `URL` with no scheme and no host, which:

- takes precedence over the discovered server (`??` never falls through), and
- makes `appendingPathComponent` produce a schemeless URL that `URLSession` rejects,
  failing every request with an opaque error.

Meanwhile `ContentView:52` uses a *different* rule for display — `!customServerURL.isEmpty
? URL(string:) : activeServerURL` — so the UI can show "Connected to Server" for a URL the
sync path treats differently. `DashboardView:175` has yet a third variant using
`resolvedURL`. Three inconsistent resolutions of the same question.

**Fix:** centralize server-URL resolution in one function that validates
`url.scheme != nil && url.host != nil`, returns `nil` otherwise, and is used by
`ContentView`, `DashboardView`, and `BackgroundSyncManager` alike. Surface a validation
error in `SettingsView` when the override is unparseable.

## Medium

### M1. TLS certificate validation is disabled for every host

**File:** `client/Sources/Managers/SyncEngine.swift:23-36`

```swift
if challenge.protectionSpace.authenticationMethod == NSURLAuthenticationMethodServerTrust,
   let serverTrust = challenge.protectionSpace.serverTrust {
    completionHandler(.useCredential, URLCredential(trust: serverTrust))
}
```

This accepts **any** server certificate for **any** host, unconditionally. The comment
claims "User verified in settings", but no verification occurs anywhere in the codebase —
the approval flow in `ContentView:195-215` approves a *URL string*, never a certificate.

The threat is concrete given the architecture: the app auto-discovers servers over mDNS on
whatever Wi-Fi it joins, and mDNS is unauthenticated and trivially spoofed. Anyone on the
same network can advertise `_datadonor._tcp`, and if the user approves the prompt (which
shows only a host:port), the app uploads a complete health history over a TLS connection
that validates nothing. The API key is sent as a bearer token to that host, so it is
disclosed too.

Note this is a deliberate design tradeoff for self-signed certs, not an oversight — but
the current form is broader than needed.

**Fix:** pin the certificate. On first approval, store the server's SPKI hash alongside the
approved URL; on later connections compare and reject on mismatch. `SecTrustCopyKey` +
SHA-256 over the DER-encoded public key is sufficient. At minimum, scope the blanket trust
to hosts present in `approvedServers`.

### M2. Ingestion endpoint trusts client-supplied `device_id`, enabling cross-device data tampering

**File:** `server/app.js:76-90`, `server/app.js:117-122`

Authentication is a single shared API key (`app.js:30-42`); there is no per-device
credential. `device_id` arrives in the request body and is used directly as the write key.
Likewise `/checkpoint` and `/stats` accept `X-Device-ID` as a header with no binding to the
authenticated principal.

Any holder of the API key can therefore read another device's checkpoints and stats, write
records attributed to another device, or — via `deleted_uuids` — **delete arbitrary rows**:

```js
const deleteStmt = await db.prepare(`DELETE FROM health_metrics WHERE uuid = ?`);
```

The DELETE is not scoped by `device_id`, so a payload can remove any record in the table
regardless of which device owns it.

For a single-user self-hosted deployment this is largely theoretical, but the shared key is
also printed as a QR code and typed into phones, so it is not a strong secret.

**Fix:** at minimum scope the delete —
`DELETE FROM health_metrics WHERE uuid = ? AND device_id = ?`. Longer term, issue
per-device tokens and derive `device_id` from the token rather than the request body.

### M3. Serialized write queue drops errors and can wedge the endpoint

**File:** `server/app.js:74-179`

```js
let dbQueue = Promise.resolve();
...
return new Promise((resolve, reject) => {
    dbQueue = dbQueue.then(async () => { ... });
});
```

Three problems in this construction:

1. **`reject` is never called.** Every path calls `resolve`, including the error path
   (line 175). That is intentional, but it means the outer promise's `reject` is dead code
   and any exception thrown *outside* the inner `try` — e.g. by `getDb()` at line 87 if the
   DB is unavailable — rejects `dbQueue` itself. There is no `.catch` on the chain, so
   `dbQueue` becomes a rejected promise and **every subsequent request hangs forever**
   (its `.then` callback never runs, the response promise never settles). One transient DB
   failure bricks ingestion until restart.
2. **Unbounded queue growth.** Requests serialize with no depth limit; the client's
   fire-and-forget uploader (C3) can enqueue thousands of concurrent batches, each holding
   a Fastify request open.
3. **Rollback races.** The `ROLLBACK` at line 171 runs on the shared connection. If the
   failure occurred before `BEGIN TRANSACTION` succeeded, this throws "cannot rollback - no
   transaction is active", which is caught and logged — harmless — but it means a genuine
   rollback failure is indistinguishable from a benign one in the logs.

**Fix:** append `.catch(() => {})` to the `dbQueue` assignment so the chain can never stay
rejected; move `getDb()` inside the `try`; add a queue-depth cap that returns 503 when
exceeded.

### M4. `totalRecordsSynced` is written from two sources and races

**File:** `client/Sources/Managers/HealthQueryManager.swift:211-214`

```swift
DispatchQueue.main.async {
    self.totalRecordsSynced += recordsCount          // async, on main
}
UserDefaults.standard.set(
    UserDefaults.standard.integer(forKey: "totalRecordsSynced") + recordsCount,
    forKey: "totalRecordsSynced")                    // sync, on current thread
```

The published property and the persisted value are updated independently, on different
threads, with a read-modify-write on the `UserDefaults` side that is not atomic. `@Published`
is also mutated off the main actor elsewhere. The two values drift, and the drift persists
across launches because line 9 seeds the property from `UserDefaults`.

Additionally `performSync` overwrites both from the server's `total_records` (line 278-281)
while in-flight uploads from the *previous* run may still be incrementing them.

**Fix:** make `HealthQueryManager` fully `@MainActor` (it is already annotated at line 5,
but `nonisolated` writes leak through `DispatchQueue.main.async`), update the property on
the main actor and derive the persisted value from it in one place.

### M5. Server startup ignores the DB initialization failure path

**File:** `server/db.js:102-105`, `server/app.js`

```js
dbPromise = setupDatabase().catch(err => {
    logger.error(...);
    process.exit(1);
});
```

The `.catch` returns `undefined` after calling `process.exit`. `process.exit` is not
instantaneous when async work is pending, so between the catch and actual termination,
`await getDb()` resolves to `undefined` and every handler throws
`TypeError: Cannot read properties of undefined (reading 'all')` — reported to clients as a
generic 500 rather than the real cause. It also makes `db.js` untestable, since importing
it can kill the test runner.

**Fix:** export the raw promise, let it reject, and handle the failure in `app.js` before
`fastify.listen`.

### M6. Timezone mismatch between ingestion buckets and the backfill/rebuild path

**Files:** `server/app.js:128`, `server/db.js:87-92`, `server/rebuild_aggregations.js:13-18`

Live ingestion buckets by string slicing:

```js
const dateStr = metric.start_date.split('T')[0];
```

The backfill and rebuild paths use SQLite's `date(start_date)`, which **converts to UTC**
when the timestamp carries an offset. Verified: `date('2026-08-04T23:30:00+03:00')` returns
`2026-08-04`, while the string split of the same value also returns `2026-08-04` — they
agree only because SQLite's conversion happens to land on the same day here; for
`2026-08-04T23:30:00-05:00` they diverge (`2026-08-05` vs `2026-08-04`). **[verified]**

The client currently sends UTC `Z` timestamps via `ISO8601DateFormatter`, so the two agree
today — but running `npm run rebuild-stats` after any client change to local-time
formatting would silently shift buckets by a day.

Separately: bucketing by UTC means a user's "day" in the chart is not their local day.
Samples after 17:00 PDT are counted toward tomorrow.

**Fix:** pick one representation (UTC-normalized is fine) and use it in all three places;
consider storing an explicit `local_date` column derived from the sample's offset.

### M7. Unit mismatches are silently stored as `0.0`

**File:** `client/Sources/Managers/HealthQueryManager.swift:87-93`

```swift
} else {
    value = 0.0
    DataDonorLogger.shared.log("Unit mismatch: ... Storing 0.0.", level: .warn)
}
```

A `0.0` is indistinguishable from a genuine zero measurement once in the database. For a
tool whose purpose is faithful data extraction, this corrupts the archive rather than
surfacing the problem — and since anchors advance regardless, the correct value is never
re-fetched.

The `default:` branch of `unit(for:)` (line 59) returns `HKUnit.count()` for any
unrecognized identifier, making mismatches likely whenever Apple adds a type.

**Fix:** skip the sample (return `nil` from `mapSample`) so it is not persisted with a
false value, or send `null` and record the incompatibility in `metadata`.

## Low

### L1. `db.prepare` inside a loop without `reset` — `finalize` ordering

**File:** `server/app.js:94-114`

A single prepared statement is `run` repeatedly in a loop. With the `sqlite` wrapper this
works, but `stmt.finalize()` is called *inside* the `try` (line 114). If any `stmt.run`
throws mid-loop, the statement is never finalized and leaks until GC — while the
`ROLLBACK` in the catch runs on a connection that still has an open statement.

**Fix:** finalize in a `finally` block.

### L2. Log parsing breaks on messages containing `]`

**File:** `client/Sources/Views/LogViewer.swift:114-118`

`line.split(separator: "]", maxSplits: 2, ...)` takes `parts[2]` as the message. Because
`maxSplits: 2` caps the split, a message containing `]` survives intact — this is correct.
However, `parts[1].dropFirst()` assumes exactly one leading character (` [`) — the writer
emits `"[LEVEL] [TIMESTAMP] message"`, so `parts[1]` is `" ["` + timestamp and
`dropFirst()` removes the space, not the bracket. The bracket is then removed by
`trimmingCharacters(in: .whitespaces)`... which does **not** trim `[`. Timestamps therefore
render with a stray leading `[`.

**Fix:** parse with a regex, or `trimmingCharacters(in: CharacterSet(charactersIn: " ["))`.

### L3. LogViewer writes fake log entries as a side effect of being opened

**File:** `client/Sources/Views/LogViewer.swift:81-90`

If no logs exist, the view **writes three fabricated entries** ("Initialized
DataDonorLogger", "Checking HealthKit permissions...", "Waiting for network connection.")
to the real log file. These are indistinguishable from genuine records and persist. A
debugging tool that manufactures evidence actively misleads.

**Fix:** delete the block; show the existing "No logs found." empty state.

### L4. Dead code: `NotificationManager` and `setupObserverQueries` are never called

**Files:** `client/Sources/Managers/NotificationManager.swift`, `client/Sources/Managers/BackgroundSyncManager.swift:49-69`

Confirmed by grep — neither has a call site outside its own definition. So:

- No sync-error notification ever reaches the user; failures are invisible (compounding C3).
- `enableBackgroundDelivery` is never invoked, so HealthKit never wakes the app on new data.

Relatedly, `DataDonor.entitlements` lacks
`com.apple.developer.healthkit.background-delivery`, which is **required** for
`enableBackgroundDelivery` to succeed. Wiring up `setupObserverQueries` without adding that
entitlement will fail at runtime with the error swallowed by the `if !success` print at
line 66.

**Fix:** either wire both up (adding the entitlement and requesting notification
authorization at launch) or delete them so the codebase reflects actual behavior.

### L5. `HealthDataValue` decodes numbers as strings

**File:** `client/Sources/Models/HealthDataPayload.swift:45-57`

`init(from:)` tries `String.self` **before** `Double.self`. This is only used if the app
ever decodes a payload (it currently only encodes), but the ordering means a JSON number
would still decode as `.double` — correct — while a JSON string `"42"` decodes as
`.string`. Fine today; fragile if round-tripping is added.

### L6. `resolvedURL` is a documented-legacy field still driving the dashboard

**Files:** `client/Sources/Managers/ServerDiscoveryManager.swift:8-10`, `client/Sources/Views/DashboardView.swift:141,175`

`resolvedURL` is commented "Legacy support ... though we'll remove uses of it", yet
`DashboardView` still depends on it for both refresh triggering and URL resolution. Crucially
it is set **before** user approval (line 77, outside the approved/pending branch), so the
dashboard sends the API key to an unapproved, possibly spoofed server the moment it
resolves — bypassing the approval gate that `activeServerURL` implements.

**Fix:** delete `resolvedURL`; point `DashboardView` at `activeServerURL`.

### L7. Stray files and inconsistent naming

- `test.swift` (repo root) — a scratch snippet testing a JSON cast, untracked. Delete or move.
- `server/copy.json.example.json` — duplicate of the tracked `server/config.json.example`,
  with a confusing double extension. Delete.
- `server/package.json` declares `"main": "index.js"`, but no `index.js` exists (entry point
  is `app.js`). Also `"license": "ISC"` contradicts the MIT license in `README.md`.
- `server/package.json` has no `"start"` script despite `ecosystem.config.js` running `app.js`.
- `check_bg.py` / `plot_metrics.py` at the repo root are undocumented in the README.

### L8. QR scanner stops the session before validating the payload

**File:** `client/Sources/Views/QRScannerView.swift:87-96`

`captureSession.stopRunning()` is called unconditionally at the top of the delegate, before
the `guard`s. If the scanned object is not a readable code or has a nil `stringValue`, the
guards return, `onResult` is never called, the sheet stays open, and the camera is dead —
the user sees a frozen preview with no way to retry except dismissing.

Also `stopRunning()` is invoked on the main queue (the delegate queue set at line 48), which
Apple documents as blocking; it can hitch the UI.

**Fix:** move `stopRunning()` after the guards, onto a background queue, and only on a
successful read.

### L9. Missing `NSHealthUpdateUsageDescription` need, and over-broad permission strings

**File:** `client/Info.plist:37-38`

The app calls `requestAuthorization(toShare: nil, read:)` — it never writes health data.
`NSHealthUpdateUsageDescription` is therefore unnecessary and its text ("needs access to
write your health data") is inaccurate and may draw App Store review scrutiny.

`NSLocationWhenInUseUsageDescription` is likewise present, but no location API is used
anywhere in the codebase (the README's "SSID monitoring" feature is not implemented —
there is no `NEHotspotNetwork` or `CNCopyCurrentNetworkInfo` call).

**Fix:** remove both unused keys; correct the README's feature list.

## Documentation accuracy

The README describes three features that are not present in the code:

1. **"Network Path Monitoring — restricts data syncing to a specific Wi-Fi SSID."** No SSID
   check exists. No `NWPathMonitor`, `NEHotspotNetwork`, or `CNCopyCurrentNetworkInfo` usage
   anywhere. The `com.apple.developer.networking.wifi-info` entitlement is granted but unused.
2. **"Automatic background syncs."** Never scheduled (H3).
3. **"Background URLSession ensures massive payloads successfully upload."** The session is
   configured correctly, but success is never verified and failures lose data (C3).

## Suggested remediation order

1. **C1** — ignore and remove the health database (minutes, prevents a privacy incident).
2. **C3 + H3 + H4** — make sync delivery verifiable and actually schedule it; these are one
   coherent change to the sync path.
3. **C2 + H1** — correct the counters and the dedup constraint, then `npm run rebuild-stats`.
4. **M1** — pin certificates, or scope the trust exception to approved hosts.
5. **M3 + M5** — harden the server's error paths.
6. **H2, H5, M2, M4, M6, M7** — correctness cleanups.
7. **L1–L9** — hygiene; fold into whichever change touches the file.

# Remediation log

All findings were fixed on 2026-08-04. Two new client files were added
(`ServerResolver.swift`, `ServerTrustStore.swift`) and registered in the Xcode project.

## Verification performed

- **iOS client:** `xcodebuild … clean build` succeeds with **zero errors and zero warnings**
  in project sources. Also built with `SWIFT_STRICT_CONCURRENCY=complete`; every warning
  introduced by these changes was resolved, leaving only pre-existing ones inherent to
  non-Sendable Apple SDK types (`AVCaptureSession`, `HKHealthStore` callbacks, `NetService`).
- **Server:** booted for real over HTTPS against a scratch database and exercised live via
  `curl` — auth paths (200/401/403, including a length-mismatched key that would previously
  have thrown in `timingSafeEqual`), payload validation, ingestion idempotency, checkpoints,
  and both `months` and `weeks` stats.
- **Data-layer regressions:** a standalone harness against real SQLite covering C2, H1, H2,
  M2 and M6 — all pass. Live confirmation: posting an identical payload four times yields
  `count: 1` per bucket (previously 4), and one device cannot delete another's rows.
- **Production database:** checked for pre-existing counter drift —

## Note on the SSID feature

The README's "Network Path Monitoring / restricts syncing to a specific Wi-Fi SSID" claim
described functionality that was never implemented — there is no location or network API
call anywhere in the client. Rather than build a new feature under the banner of a bug fix,
the claim was removed from the README. The `com.apple.developer.networking.wifi-info`
entitlement is still granted but unused; implementing SSID restriction remains open work.
